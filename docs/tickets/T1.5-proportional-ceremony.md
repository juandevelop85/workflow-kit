# T1.5 · Proportional ceremony: change lanes (ODD)

> **Status:** ✅ Done
> **Phase:** Phase 1 (credibility)
> **Priority:** High
> **Date:** 2026-11-01
> **Depends on:** T1.4
> **Origin:** request (adapt Organic Driven Development: the flow is common, its execution adapts to the work)

## Description

Every change, a typo included, paid the full process: ticket, tests first, gates, backlog, review,
a five-part commit body. That makes a kit slow to use and teaches people to skip it. ODD keeps the
same flow and scales how much of it a change runs, by judgment over risk and understanding, while
objective signals set a floor the agent cannot go under.

## Context and Decisions

- Three lanes: **quick** (well understood, localised, no behaviour risk: no ticket, gates and the
  checker still run), **standard** (a ticket, tests first, review per `review-plan`) and **deep**
  (a ticket broken into steps, explicit risk assessment, full review).
- Signals are measured, judgment is asked: the checker computes a *minimum* lane from the diff
  (size, spread, sensitive paths, code without tests, binary files, the workflow's own files); the agent answers the ODD
  questions and may only move up.
- A quick change is committed with `quick` instead of a ticket id, and `check --commits` verifies
  afterwards that each such commit really was quick (size and sensitive paths). Instructions are
  not enforcement; this check is.
- Discarded: classifying by line count alone (ODD warns against it); asking the user every time.

## Technical Scope

1. `workflow_check.py classify [--base REF] [--json]`: minimum lane and the reasons.
2. `[lanes]` settings, validated; quick commits accepted and audited by `check --commits`.
3. A `change` skill and `/change` command as the single entry point: classify, then run the lane.
4. `ticket-runner` and the docs describe the lanes.

## Acceptance Criteria

Default limits shipped in `[lanes]`: quick up to 40 changed lines in up to 5 files (docs-only: up to
300 lines), and at most 5 lines of code changed without a test change; deep from 400 lines or 15 files.

- A change within the quick limits, with no sensitive path, is quick. test: test_small_change_is_quick
- A sensitive path is never quick, whatever its size. test: test_sensitive_change_is_at_least_standard
- More than 5 lines of code changed without any test change is at least standard. test: test_code_without_tests_is_standard
- 400 lines or 15 files make a change deep. test: test_large_change_is_deep
- A quick commit that exceeds the quick limits fails `check --commits`. test: test_oversized_quick_commit_is_an_error
- A quick commit within the limits passes. test: test_honest_quick_commit_passes
- Lane thresholds are configurable and validated. test: test_lane_settings_are_validated
- Added after review (security review blocked the first version): moves count at both ends
  (test_a_move_into_a_sensitive_path_is_caught); the workflow's own files are never quick
  (test_changing_the_workflow_is_never_quick); binaries are never quick
  (test_binary_files_are_never_quick); size alone makes a change standard
  (test_size_alone_makes_a_change_standard); `.txt` is not prose (test_a_txt_or_a_script_under_docs_is_not_prose);
  quick commits still cite real tickets (test_a_quick_commit_cannot_cite_a_ticket_outside_the_backlog);
  a disabled quick lane makes standard the minimum (test_the_quick_lane_can_be_turned_off);
  `classify` validates the configuration (test_classify_refuses_an_invalid_configuration).

## Risks

Requires security review (changes what the commit check accepts). A lane is a floor, not proof of
safety: the gates still run in every lane.
